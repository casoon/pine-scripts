# Changelog

## v1.5.1 — 2026-08-01
- Fix: user reported two real problems with v1.5.0's coherent-wave merge — (1) a merged wave extended past the actual lowest/highest pivot of the move, into the start of the recovery, and (2) a genuine time gap (candles with no box at all) appeared right after that wave was flushed. Root cause: v1.5.0 decided whether to keep absorbing legs by re-scoring the whole span's *character* (IMPULSE/CORRECTION/NEUTRAL) on every leg — as long as the character held, the wave kept growing well past the true extreme, and the boundary math around the flush-then-reseed transition didn't guarantee the next wave picked up from exactly where the last one had stopped.
- Replaced with a classic Zigzag-style rule, per explicit user request ("a wave should always end exactly at the local extreme pivot"): a wave now tracks new extremes in one direction (`pendingWaveDirection`). A leg whose pivot type matches that direction only absorbs into the wave if it's an actual new extreme (`pendingWaveExtremeBar`/`Price` — exactly what gets drawn as the box's end); a leg of the opposite type (an internal counter-swing pullback/push) always absorbs unconditionally without moving the tracked extreme. The wave flushes — ending exactly at its last real extreme, never past it — the instant a same-direction leg fails to extend further, and the next wave is explicitly seeded starting from that same extreme bar/price (recomputing its own high/low over just that span via `f_calculateLeg`), which is what guarantees zero time gap between two consecutive drawn boxes.
- The wave's whole-span DNA classification (IMPULSE/CORRECTION/NEUTRAL, for the label/color and the RANGE-vs-normal-leg decision) is now computed once at flush time only, not on every leg — it no longer drives the absorb/flush decision itself.
- Removed `pendingWaveClass`/`pendingWaveEndBar`/`pendingWaveEndPrice` (no longer meaningful under the new rule); added `pendingWaveDirection`/`pendingWaveExtremeBar`/`pendingWaveExtremePrice`.

## v1.5.0 — 2026-08-01
- User pointed out (drawing a hand-annotated zigzag over a chart) that a clean, decisive climb was fragmented into many small alternating boxes (e.g. "RANGE(2)", "CORRECTION", "CORRECTION", "CORRECTION" in a row) instead of showing as one continuous move to the peak — each small piece is individually a real, correctly-classified small pullback/push (this is not a scoring bug, matching classic sub-wave structure), but the *drawing* didn't recognize that the whole climb net decisively agreed in one direction.
- Generalized v1.4.0's NEUTRAL-only merge into a general coherent-wave merge: every completed leg is now folded into a running "wave" as long as re-scoring the *whole span* (the wave's first pivot through the newest leg, via the same DNA scoring as any other leg) keeps agreeing with the wave's established class. The moment absorbing a new leg would change that whole-span verdict, the wave is drawn as one box (pivot to pivot) and a fresh wave starts, seeded by that leg. This replaces v1.4.0/v1.4.3's NEUTRAL-specific streak logic — NEUTRAL runs are now just one case of the same general mechanism (a wave whose class happens to stay NEUTRAL still gets the "RANGE (Nx)" treatment once it reaches "Minimum consecutive legs to merge into one wave"; any other class draws as a normal leg regardless of count).
- Renamed accordingly: `mergeNeutralLegsInput` → `mergeCoherentLegsInput` ("Merge consecutive legs into one coherent wave"), `minRangeLegsInput` → `minWaveLegsInput`, `pendingRange*` state → `pendingWave*` (now also tracks `pendingWaveClass`, the wave's currently-agreed character).
- Behavior change to be aware of: every leg now has a one-leg drawing delay when merging is on (whether it gets absorbed into the ongoing wave is only known once the *next* leg completes) — this was already implicitly true for NEUTRAL streaks since v1.4.0, now it applies universally. The always-visible LIVE box is unaffected and still shows the currently developing leg with no delay.

## v1.4.4 — 2026-08-01
- Fix: user reported two adjacent CORRECTION boxes overlapping in time — a small leg visibly truncated by a large box starting before it ended ("boxes should always go correctly between two pivots"). Root cause: the same-type-pivot-extreme "replace" tie-break redraws "the last completed leg" using `pivotBars[lastIndex - 1]` as its start — the pivot immediately before the one being extended. That's only correct if the last *drawn* box was a single ordinary leg. Since v1.4.0/v1.4.3, one drawn box can span *several* original pivots (a merged range, or a whole streak reclassified as one leg), so `pivotBars[lastIndex - 1]` can point to a pivot *inside* the last drawn box, not its true start — the redraw then only recreated a small fraction of what `f_deleteLastCompletedDrawing()` had just correctly deleted, leaving the rest of that span either overlapping the next box or gapped.
- Fixed by tracking `lastDrawnLegStartBar`/`lastDrawnLegStartPrice` explicitly — updated every time a leg/range is actually drawn — and using that (not a `pivotBars` lookup) for the tie-break redraw. This is correct regardless of how many original pivots the last drawn box represents.
- This is a real correctness fix, not cosmetic: box boundaries should always land exactly on confirmed pivots with no gap or overlap in time (vertical/price overlap between adjacent boxes remains normal and expected in ranging markets).

## v1.4.3 — 2026-08-01
- Fix: user reported a "RANGE (9)" box spanning a huge price move — a clean, decisive multi-leg decline followed by re-basing, clearly not a bounded/flat consolidation, yet merged into one range box. Root cause: v1.4.0 merged legs purely by classification (a run of individually-NEUTRAL legs), without checking whether the aggregate span actually behaves like a contained range. A sequence of small, choppy, individually-weak legs can still net a large directional move (each piece unconvincing on its own, e.g. due to internal overlap, but the whole sequence clearly trended).
- Fix: before drawing a merged range, the whole streak (first pivot to last pivot) is now re-evaluated as one continuous leg through the same DNA scoring every other leg gets (Efficiency/Overlap/Retracement over the *full* span, not per small piece). If that whole-span evaluation is decisively IMPULSE or CORRECTION, it's drawn as one normal leg box (pivot to pivot, correctly colored/labeled) instead of a generic "RANGE" — only a whole-span verdict that's *still* NEUTRAL gets the merged range treatment. This directly addresses the reported expectation: "boxes should visibly go from pivot to pivot for waves."
- This uses the existing scoring machinery rather than an ad-hoc "is this bounded" heuristic (e.g. comparing net distance to the price envelope) — Efficiency/Retracement/Overlap already measure exactly this (net progress vs. total back-and-forth), just now applied at the whole-streak scale too.

## v1.4.2 — 2026-08-01
- Follow-up decision on v1.4.1's open question (re-derive all segments vs. leave them as tracked live history): decided to re-derive. Every non-final segment's class is now recomputed at leg-completion time using `f_calculateLeg(..., isComplete=true)` (undamped, maturity=1.0) instead of trusting the maturity-damped/hysteresis-buffered class that was tracked live — the same treatment the leg's own overall classification already gets. `liveSegmentClasses`/`segClasses` is no longer used for coloring at all, only for detecting *where* a segment boundary falls during live tracking; removed the now-unused `segClasses` parameter from `f_drawCompletedLeg` and both remaining call sites accordingly.
- Cost: up to `maxSegmentsPerLegInput - 1` extra `f_calculateLeg` calls per completed leg (a one-time event per pivot, not a per-bar cost, so not added to the existing live-leg performance concern in todo.md).

## v1.4.1 — 2026-08-01
- Fix: a completed leg's label could show `IMPULSE`/`CORRECTION` while its box rendered fully `NEUTRAL`-colored (user report, screenshot of an IMPULSE-labeled leg with a solid tan box). Root cause: the label uses the final, undamped classification (`isComplete=true`, no maturity ramp), but segment colors come from `liveSegmentClasses`, captured during the live phase using the maturity-damped, hysteresis-buffered `liveClassState` — the same class of bug the v1.0.1 fix addressed for the leg's own overall score, just resurfacing in the segment-tracking path that fix never touched. A short leg (under "Bars until full score maturity", default 8) spends its *entire* live history damped toward neutral, so every tracked segment can disagree with the final verdict.
- Fixed the immediate symptom: the *last* segment (the one directly adjacent to the label) now always uses the final `legClass` instead of its tracked live class. Earlier segments are left as tracked — they're meant to show the leg's actual character evolution, not get overridden.
- Not fully fixed: earlier segments of a short/young leg can still all read more neutral than hindsight would suggest, since maturity damping applied throughout the leg's entire live tracking, not just its first few bars, when the leg itself is shorter than the maturity window. Whether to retroactively re-derive segment classes without damping (a bigger change to what segment coloring means) is an open design question — see todo.md.

## v1.4.0 — 2026-08-01
- New feature, not a bug fix: a user asked why a visually-cohesive flat/choppy stretch was drawn as several small adjacent boxes instead of one — that's architectural, not a bug. The pivot engine works strictly swing-to-swing (confirmed pivot → next confirmed pivot), so a genuine consolidation legitimately decomposes into several small alternating legs, each of which correctly reads NEUTRAL on its own (no swing in a flat range shows strong efficiency/low overlap in isolation). This partly explains earlier "too much NEUTRAL" reports: not miscalibrated single legs, but the wrong analysis unit for "one flat zone."
- "Merge consecutive NEUTRAL legs into one range" (default on): a run of at least "Minimum consecutive legs to merge into a range" (default 2) consecutive NEUTRAL legs is now drawn as a single merged range box + "RANGE (Nx)" label instead of one box per leg. Implementation defers drawing a NEUTRAL leg until it's known whether the streak continues (a non-NEUTRAL leg, or the streak ending below the merge threshold, flushes it — either as the merged range or, if the streak never reached the threshold, as a single normal leg box, same as merging being off).
- Known interaction: the rare same-type-pivot-extreme "replace" tie-break (an already-registered pivot getting extended by a more extreme candidate of the same type) is handled two ways depending on state — if the leg it would extend is still an undrawn pending range, the range's bounds are stretched in place (nothing was drawn yet, so nothing to delete); otherwise it deletes and redraws the single already-drawn leg as before. This avoids a real bug the naive version would have hit: deleting the wrong (older, unrelated) box when the "last completed leg" was actually still deferred inside a pending range.
- Does not change any individual leg's classification — purely which boxes/labels get drawn for a run of NEUTRAL legs.

## v1.3.3 — 2026-08-01
- Fix: `CE10088 Cannot modify global variable "lastCompletedLabelBar" in function` — the v1.3.2 label-spacing fix reassigned a global scalar (`:=`) from inside `f_drawCompletedLeg`, which Pine only allows for the main script scope, not from within a function. Functions may mutate a collection's *contents* (arrays, boxes, labels) but not rebind a plain global variable. Fixed by moving the tracked value into a single-element `array.new_int(1, na)` (`lastCompletedLabelBarBox`), read/written via `array.get`/`array.set` — the same reference-type workaround already used for every other piece of cross-call state in this file (`completedBoxes`, `completedBoxCounts`, etc.).
- Audited every other `:=` in the file for the same mistake: everything else is either a local variable inside a function (always fine) or top-level main-script-scope code (also fine — the restriction is specifically about reassigning an outer variable *from inside* a `=>` function body).

## v1.3.2 — 2026-08-01
- Fix: completed-leg labels had no collision avoidance — when two legs were short/close together (common in choppy stretches, same conditions that already tend to produce NEUTRAL legs), their labels stacked directly on top of each other, reading as a garbled overlap (user report: two "CORRECTION" labels overlapping) or as an apparently "missing" label on a middle leg of a tight cluster (the label was actually being created, just rendered invisibly behind its neighbor).
- New input "Minimum label spacing (bars)" (default 3, Labels group): a completed leg's label is now skipped outright if it would land closer than this to the previous completed leg's label. The leg's colored envelope (and segment coloring) is always drawn regardless — only the label/tooltip is affected, so a tightly-packed cluster of short legs shows fewer labels but the same box colors as before.
- This does not change any Impulse/Correction/Neutral classification — purely a label-rendering fix.

## v1.3.1 — 2026-08-01
- Fix: crash `array.get() Index 0 is out of bounds, array size is 0` in `f_calculateLeg` (v1.3.0's sub-swing growth loop). Root cause: a Pine `for i = from to to` loop with no explicit `step` counts *downward* when `to < from`, instead of not executing — `for swingIdx = 0 to completedSwings - 1` becomes `0 to -1` when a leg has zero completed internal sub-swings, which iterates for swingIdx=0 and -1 (2 passes) rather than 0. Guarded with `if completedSwings > 0` before the loop.
- Same unguarded-loop pattern existed in two more places already shipped in earlier versions and is fixed here too: `f_trimDrawings`'s `for i = 1 to oldCount` and `f_deleteLastCompletedDrawing`'s `for i = 1 to lastCount`, both reachable whenever a leg contributed zero boxes (e.g. "Show completed leg envelopes" off) — both now guarded with `if ... > 0`. Not yet observed as a live crash, but the same shape as the fixed bug.

## v1.3.0 — 2026-08-01
- Roadmap Phase 1.3 (Internal Sublegs), continued: two more diagnostic-only metrics per leg, both reusing the v1.2.0 sub-pivot infrastructure —
  - **Progression-to-rotation ratio**: net leg distance divided by the total internal sub-swing distance (`netDistance / internalSwingSum`, clamped 0–1). High = swings walked almost straight toward the net move with little back-and-forth; low = a lot of internal rotation for little net progress.
  - **Sub-swing growth ratio**: average size of the second half of completed internal sub-swings vs. the first half (same first/second-half split already used for Momentum/TR expansion). Above 1 = sub-swings are expanding as the leg develops, below 1 = contracting.
- Both are exposed in the tooltip (new "Progression · Trend" line) and Data Window; neither feeds the Impulse/Correction score, same rationale as v1.2.0's sub-swing count/size (prep for the Phase 2 ABC engine, not a new score input to calibrate today).
- Still open from Phase 1.3: structural (not candle-range) overlap between sub-swings — needs tracking each sub-swing's own price range, not just its size, deferred (see todo.md).

## v1.2.0 — 2026-08-01
- Follow-up to the v1.1.2 momentum fix: a second user-reported tooltip still showed `Mom 100.0` on a visually corrective leg — the 0.1×ATR floor was too small to stop a merely moderate second-half push from saturating the ratio. Raised the floor to 0.25×ATR so only a genuinely strong push maxes out Momentum.
- Roadmap Phase 1.3 (Internal Sublegs), partial: each leg now tracks its own internal sub-pivot structure (a smaller, independent `ta.pivothigh`/`ta.pivotlow` pass scoped by the new "Internal sub-pivot width" input, default 2 bars) and reports internal sub-swing count and average sub-swing size (in ATR multiples, for cross-instrument readability) in the tooltip and Data Window. Diagnostic only — deliberately does not feed the Impulse/Correction score, per the roadmap's own framing of this data as prep for the future ABC engine (Phase 2), not a new DNA weight to calibrate today.
- Not done from Phase 1.3: progression-to-rotation ratio, growing/shrinking subleg size trend, structural (not just candle-range) overlap — deferred, see todo.md.

## v1.1.2 — 2026-08-01
- Code audit (via `indicator-code-audit`) triggered by a user report that visually corrective legs were scoring near 50/50 instead of clearly corrective, plus several tooltip breakdowns showing suspicious values. Fixed the two bugs confirmed by that data plus one repaint issue:
  - **Momentum expansion fallback**: when a leg's first half had ~zero trend-aligned candle body, `momentumRatio` used to hard-jump to the fixed `momentumHighRatioInput` constant regardless of how small the second half's actual push was, always saturating Momentum to 100% — this alone explained 3 of 4 user-reported NEUTRAL legs showing `Mom 90–100` despite reading as clearly corrective. Now floors the ratio's denominator with a fraction of ATR instead, so it scales with the real move size.
  - **Efficiency's mixed price reference**: `netDistance` (from the actual pivot high/low) and `pathDistance` (previously a sum of close-to-close deltas) used two different price bases inside one ratio, which could make Efficiency read impulsively high even on a choppy leg whenever the leg's boundary bars had prominent wicks — this produced the internally contradictory `Eff 74.9 / Ret 92.2` pairing from a reported tooltip. `pathDistance` now sums each bar's true range (already computed for the TR-expansion feature) instead of close deltas, so both sides of the Efficiency ratio are wick-based. **This changes Efficiency's numeric output** — expect different (generally lower on choppy legs) Efficiency values than v1.1.1 and earlier.
  - **Alert repaint**: `becameImpulse`/`becameCorrection`/`lostCharacter` alerts fired on every realtime tick with no bar-close gate, so a live character flip could alert and then revert before the candle closed. Added "Alerts only on bar close (confirmed)" (default on), matching the convention used elsewhere in this repo.
- Deferred (see todo.md): "Wick cleanliness" is direction-agnostic (measures body/range ratio, not which side the wick sits on) — a concept-vs-name mismatch, not fixed here since it's a definition change; the live leg's full O(bars) DNA recompute on every realtime tick (performance) is unaddressed; the dead `avgFirstTr > mintick` fallback branch in TR expansion is unreachable in practice but harmless.

## v1.1.0 — 2026-08-01
- Segment-level leg coloring (Phase 1.1 of the roadmap): a completed leg's envelope is now split into colored segments at every bar where the live leg's character changed while it was still forming, instead of drawing one solid-color box for the whole move. The segment boundary itself is the character-change marker — no separate marker object was added. Historical score-trajectory storage and a multi-part gradient overlay remain open (see todo.md).
- New input "Maximum color segments per leg" (default 6) caps segment count on unusually choppy legs; further character changes beyond the cap keep the last segment's color.
- `max_boxes_count` raised 300 → 400 for the added segment-box headroom.

## v1.0.1 — 2026-08-01
- Fix: the maturity ramp (`evaluatedBars / minimumMatureBarsInput`) was applied to completed legs as well as the live leg, forcing any completed leg shorter than the maturity window to NEUTRAL regardless of how decisive its actual score split was (e.g. a 7-bar leg with a 62.7/37.3 Impulse/Correction split was displayed as NEUTRAL). Completed legs are done growing by definition, so `f_calculateLeg` now takes an `isComplete` flag and only applies the maturity ramp to the still-developing live leg — completed legs get full maturity (1.0) and classify purely on their score separation.
